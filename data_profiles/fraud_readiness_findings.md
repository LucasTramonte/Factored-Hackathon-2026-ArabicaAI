# Fraud-modeling readiness: findings

Roberto, 28 September 2026. Source: [fraud_readiness_audit.md](fraud_readiness_audit.md), generated by [fraud_readiness_audit.py](fraud_readiness_audit.py) from a full S3 pipeline run (quality run `20260928T214210Z`: READY, 0 errors, 6 known warnings). Synthetic data. These findings close the 26/09 task "audit amount normalization, geography aliases and feature/label timing before fraud modeling."

## Decision

**Keep `fraud_score` out of every model and every intake decision.** It is deterministically tied to the label, and this snapshot cannot show which was set first, so treat it as leaking the label. `is_fraud` has no availability timestamp, so a fraud baseline's timing cannot be validated from this snapshot. V1 intake is unaffected: it uses original amount and currency and never reads either field.

## Findings

1. **`fraud_score` is tied to the label; treat it as leakage.** No non-fraud row scores above 30.0. Of 3,425 scored fraud rows, 2,373 (69.3%) score above 30.0, and every score above 30.0 is fraud. Overall AUC is 0.8468 only because the other 31% of fraud rows overlap the non-fraud range. Either the score was derived from the label, or the label was set by a rule on the score (then the score would be a legitimate upstream feature). One snapshot cannot separate these, so it cannot be used safely until the organizers confirm its provenance.
2. **Label timing cannot be established.** There is no label timestamp. `process_date` equals the transaction's calendar date or falls one day before it for every row (lag −1 to 0 days, same for both classes), so it carries no label-arrival information. 1,106,307/4,425,008 rows (25.0%) have `process_date` one day earlier, which is consistent with a timezone boundary rather than a delay. A time-based split with an assumed label delay is possible, but that delay would be an unvalidated assumption.
3. **Country aliases are resolved.** Silver leaves 6 canonical transaction countries and 3 `ip_country` values, with no residual spelling variants. The `México`/`Mexico` split from the Bronze profile no longer appears.
4. **Mexico has no peso amounts.** The data has no `MXN` currency: 2,126,409 Mexican transactions are recorded in `USD`. Every currency appears in every country. Never read `currency` as the country's local currency, and never assume Mexican amounts are pesos.
5. **The FX fill is noisy, not biased.** Where the source supplies `amount_usd`, the daily rate misses it by more than 1% on 593,669/1,134,663 COP rows and 361,501/752,317 ARS rows, with median ratios of 1.0 and 0.9994. The 99,442 Silver-estimated USD values (`amount_usd_is_estimated`) inherit that per-row noise. Sums can be caveated; per-transaction USD values are unreliable. 35 rows still have no USD value.

## Consequences

- **V1 intake:** show and confirm the original amount and currency only. No FX conversion and no fraud fields (already in the [contract](../Docs/intake/customer-and-measurement-contract.md)).
- **Fraud-prevention track:** blocked for this cycle. Reopening it needs a label timestamp, or a score computed before the label, from the organizers.
- **Monetary reporting:** report native USD and source-supplied USD separately from FX-estimated values, as AGENTS.md already requires.
