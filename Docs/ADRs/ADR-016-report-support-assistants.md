# ADR-016 — Bounded report support assistants

- **Status:** Proposed; implementation approved, live pilot and activation pending separate human approval
- **Date:** 2026-10-04
- **Deciders:** Lucas Tramonte, Manoella R, Roberto Z
- **Related:** ADR-002, ADR-003, ADR-004, ADR-012, ADR-014, ADR-015

## Context

Human messages and deterministic report status help already use the Worker and D1. Reviewer summaries/drafts and interpretation of a customer's report question expand the model-input scope beyond the frozen extractor. Extraction approval and its evaluation do not establish permission or quality for these tasks. The user approved six sequential implementation tasks on one branch and one final PR; no live provider trial or activation was approved.

## Decision

1. **One online runtime and independently default-off paths.** `ASSIST_REVIEWER_ENABLED`, `ASSIST_CUSTOMER_ENABLED` and `ASSIST_DISCOVERY_ENABLED` enable only when exactly `1`. Reviewer assistance returns a summary, a closed missing-field checklist and an editable draft. Generation never sends a message, closes a report, refunds, blocks a card or decides fraud. Customer assistance returns only closed intent/field identifiers. Discovery accepts one remembered-charge description, returns strict criteria only, then the Worker performs a parameterized owner-scoped lookup and the browser presents no more than three returned charges for the existing explicit confirmation step. It stores no conversation or model output; a correction replaces browser-only state. Customer-visible prose and report facts come from approved localized copy and owned D1 reads, never generated prose.
2. **Synthetic-demo input only, pending approval before activation.** The server loads the selected report. Reviewer context projects original statement (2,000 code points), details (2,000), current status and newest eight human messages in chronological order (4,000 combined, trimming oldest selected bodies first). Total dynamic text is at most 8,000; omission is disclosed as `context_truncated`. Do not include raw identifiers, addresses, credentials, unrelated history or transaction lists. Embedded instructions are untrusted evidence. Customer context contains the current question only (1–2,000 code points), language and closed intent/field vocabulary. No transcript or transaction data goes to the model. Free text can itself contain personal information: broader bank text requires a new approved scope, not a switch flip.
3. **Dedicated model transport.** Choose `google/gemini-3.5-flash-lite` on the existing OpenAI-compatible Vertex endpoint, minimal reasoning, temperature zero, structured JSON schema. Reviewer max output is 1,024 tokens; customer max output is 128. Parse the complete JSON string, exact keys, valid Unicode, nonempty bounded strings and closed unique field identifiers; refuse HTML/URLs, tools and incomplete output. One call only, no retry, with a 10-second deadline covering authentication, HTTP and response reads. WIF authentication and endpoint construction are reused; extractor prompt, parsing, retries, request bytes and evaluation remain unchanged. Version `support-assist-v1@google/gemini-3.5-flash-lite` identifies this committed prompt/schema/bounds/model bundle. Any change requires a version increment.
4. **Atomic metadata reservations.** A UUID is reserved once before any call. Shared cap: 200 attempts per UTC day across sessions and features. Session-feature cap: five reservations in a rolling minute, `(now−60s, now]`. Reservations, failures and abandoned attempts retain their slot. Indexed conditional insertion checks both caps within an atomic D1 batch; duplicate UUIDs cannot obtain another slot while retained (seven days, with bounded sweep catch-up). Clients create a fresh UUID for each deliberate action; indefinite UUID tombstones are outside this bounded-retention design. Caller routes must authenticate, check report ownership and recheck live session/report snapshot before serving results. This transport alone grants no authority.
5. **No generated-text persistence.** Migration 0030 stores only UUID, hashed session, mode, report reference, creation time, outcome, latency, known token counts, unknown usage and prompt/model version. It stores no statements, questions, answers, drafts or raw identities. Reserve records the immutable non-null prompt/model bundle version before generation and conservatively records one unknown possible call, so interruption cannot look free; terminal accounting replaces it with observed attempted calls and usage. Abandoned reservations retain conservative unknown usage. Missing/partial/invalid token counts keep the call unknown, never zero-priced; independently valid input/output counts are retained as known tokens. No model/request payload is logged or returned in errors. Existing bounded idle housekeeping abandons at most 100 reservations older than ten minutes and deletes at most 100 metadata rows older than seven days per invocation, through time/pending indexes. Retention requires the existing operator sweep to run; it is not a new scheduler.
6. **Activation gates.** Keep both switches absent/off. Use separate development and held-out synthetic ES/PT/EN conversation cases, including adversarial instructions, foreign references, concurrency, stale status/messages, logout/language changes and provider failures. Agree numerical thresholds before held-out evaluation; factual mismatch, leakage, unauthorized action, invented facts or banking promises block activation. Report sample denominators, success/fallback, acceptance/edit acceptance, human-response latency, model p50/p95 including failures and measured cost. Automated explanation is neither a human reply nor resolution. Project authorization, provider permission, live schema compatibility and pilot quality remain unverified until a separately approved live pilot.

## Consequences

- **+** Human messages stay explicit and persisted through their existing idempotent route; generated exchanges stay transient.
- **+** SQL caps are shared across isolates and features, with bounded indexed housekeeping; no new dependency or runtime.
- **−** Reviewer prose still needs human inspection and dedicated groundedness evaluation. Schema validation cannot prove factual grounding or reject every malicious sentence.
- **−** Fixed attempts bound volume, not exact cost: input tokenization varies and timed-out calls may still be billed. Unknown usage stays visible.
- **−** Without regularly running existing housekeeping, expired metadata remains until a bounded sweep catches up.

## Alternatives considered

- **General autonomous chatbot or tools.** Rejected: unnecessary scope, permissions and evaluation complexity. Reopen only with an explicit new workflow decision.
- **Reuse frozen extractor prompts/schema/retries.** Rejected: these tasks differ and would break parity. Reopen only as a separately versioned evaluated extractor change.
- **Store generated conversation/drafts as human messages.** Rejected: false authorship, ordering and retention. Reopen only with an explicit AI-transcript requirement and additive schema.
- **Per-isolate counters or delete failed reservations.** Rejected: concurrency bypasses billing limits. No reopen condition while shared caps are required.

### Reviewer API source boundary (2026-10-04, Task 3)

The read-only context joins the selected acknowledged report's episode to its customer by primary key. Only `customers.source='fictitious'` is eligible; dataset-backed reports return the localized manual fallback before reservation or provider work even when the switch is enabled. The source marker is internal and never reaches the response or model. This is a synthetic-demo guard, not consent for real customer text; activation remains separately approved.

Existing incomplete handoffs append supplied details to `intake_episodes.customer_statement` with a newline. They retain no reliable original/detail boundary, and customers may themselves use newlines. Following the coordinator-approved source ruling, the reviewer input therefore carries the entire persisted composite (already limited to 2,000 code points) as `statement`, with `details=''`. No delimiter is guessed and no content is omitted on this basis; separate original/detail labeling is unavailable for these records. The newest-message projection and computed `context_truncated` still identify omitted older conversation content. No provenance migration or intake-path change is introduced.

Generation reads no transaction, unrelated customer history, identity or email, writes no message/status/first-open marker, and revalidates the presented agent session and monotonic status/message-count snapshot after the model call. Assisted message insertion checks its optional expected snapshot within the existing atomic insert, while same-key/body readback remains valid after later messages or closure. The separate human Send action alone persists the reviewed text.

### Dedicated acceptance registration and release boundary (Task 6)

The [offline evaluation foundation](../../evals/support_assist/README.md) freezes 30 development and 60 acceptance synthetic cases per feature, 10/20 per ES/PT/EN; 21 acceptance cases per feature are adversarial/unsupported. The exact acceptance and bundle hashes are in [COMMITMENT.json](../../evals/support_assist/COMMITMENT.json), frozen 2026-10-05 04:16:28 UTC before provider trials. Cases were authored after implementation and are not an independent blind benchmark; human multilingual label review remains pending. A changed bundle requires a new version and fresh acceptance set, never tuning against these outcomes.

Three repetitions mean 180 attempts per feature, all failures/fallbacks retained. Fixed proposed gates: no leak, unauthorized write, invented fact or financial promise; exact stored-source status and safe invalid/unknown fallback; ≥90% supported exact intent/field classifications overall (117 attempts), ≥85% per language (39); ≥80% usable reviewer drafts without factual correction over all 180, with unchanged and edited acceptance separate; successful-generation p95≤8 s and failed/timeout rate≤5%, with all-attempt latency separately reported. Retain the existing 10 s WIF/provider/read deadline check. Measure actual tokens/unknown usage and the verified regional prices, not extractor or mock cost/latency.

Shared 200/day and five/session/feature/minute caps constrain the live pilot too: 360 acceptance attempts need ≥2 UTC days; one development call per each of 60 cases plus acceptance needs ≥3, with failed/abandoned/other reservations consuming capacity. No cap bypass or session rotation. The offline scorer audits the complete reserved-slot ledger across UTC days and refuses missing/duplicate attempts or falsely passed mock-only evidence. Passing requires matched input hashes, named human review, configured-project/live/approval evidence and private raw-evidence commitment; hashes verify integrity and still require human provenance inspection.

Ten scripted local Worker/D1 journeys establish protocol/persistence only. **No support-assist live trial, measured spend, human handling-time comparison or production activation was performed.** Live ≥10 operator journeys, separate human-response/paired handling measurements, quality/performance acceptance and separate per-feature activation approvals remain pending. A passing score is not activation authorization. The [aggregate evidence and exhaustive controller rulings](../Evidence/support-assist-pilot.md) preserve implementation limits including seven-day UUID replay horizon, absent status-update timestamps, composite statement provenance and endpoint body/D1 timing semantics.
