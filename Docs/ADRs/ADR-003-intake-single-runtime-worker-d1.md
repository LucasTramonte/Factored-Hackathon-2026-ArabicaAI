# ADR-003 — Intake runtime: one online API on Cloudflare Workers + D1, Python for batch

- **Status:** Proposed
- **Date:** 2026-09-29
- **Deciders:** Lucas Tramonte, Manoella R, Roberto Z

## Context

Until this change the intake demo had two complete online implementations of the same API:

- FastAPI with PostgreSQL (`demo_pg/`), run locally.
- A JavaScript Cloudflare Worker with D1, deployed at the team preview URL.

Session handling, customer scoping, idempotent case creation, reference-after-commit and the agent view each existed twice. The copies had already drifted: FastAPI kept sessions in process memory, while the Worker stored them in D1.

Constraints for this decision:

- **Window.** Finalists are announced on 2026-10-15. The service has to run from 2026-09-29 until 2026-10-31, which leaves some margin after the announcement.
- **Budget.** No hosting spend. Lucas's AWS account is on the Free plan: $100 in credits, available until 2027-03-22, and no card on file, so it can't be charged. We keep those credits for estimating a later scale path, not for running the demo.
- **MVP.** Deterministic, no model calls ([ADR-002](ADR-002-v1-workflow-unrecognized-charge-intake.md)).
- **Volume.** The online store holds very little: a handful of customers, at most 20 transactions each, and dozens of cases. The heavy data (millions of rows) stays offline in DuckDB.
- **Brief requirements.** The brief asks for scalability reasoning, explicit latency and cost trade-offs, capacity limits, monitoring, access control and data retention.

## Decision

1. **A single online API.** The Cloudflare Worker in `back-end/`, written in JavaScript with ES modules and backed by one D1 database, serves the API. It also serves the Angular build from `front-end/` as static assets. `demo_pg/` is removed; git history keeps it.
2. **Python is for batch work only.** Bronze → Silver → quality → Gold intake slice (`data_pipelines/gold/`). The slice validates a bounded sample and writes a versioned D1 seed plus a manifest straight from DuckDB. Nothing in the request path reads DuckDB, Silver or S3. Evaluations call the API over HTTP.
3. **All SQL is in one module**, `back-end/src/store/d1.js`. Route handlers never build SQL. If we move to PostgreSQL through Hyperdrive, or to a Python service, this is the one module that gets replaced.
4. **Schema changes go through `wrangler d1 migrations`, not Alembic.** Migrations are numbered SQL files in `back-end/migrations/` and are tracked in D1's `d1_migrations` table. They are applied with `--local` in tests and `--remote` at deploy time, and each one is additive and reviewed.
   - **Why not Alembic:** Alembic runs inside a Python process that holds a SQLAlchemy connection to the database. D1 has no such connection. It is only reachable through the Worker binding or Cloudflare's HTTP API, and no supported SQLAlchemy dialect exists for it. Adding Alembic would mean a second schema tool that can't reach the production database.
   - **What we give up:** autogenerated migrations and down-migrations. Mistakes are fixed with a new forward migration, and a bad change can be undone with D1 Time Travel, which keeps 7 days on the Free plan.
   - **When this changes:** Alembic comes back if the online store moves to PostgreSQL behind a Python service. That move needs a new ADR that supersedes this point.
5. **Access control has two layers.** Cloudflare Access (email allowlist or one-time PIN) covers the whole hostname. The Basic gate stays as a second check on API routes and on the HTML document routes (`/`, `/index.html`, `/agent`), so the browser asks for the team credential once, on navigation. Hashed JS/CSS bundles and other static files no longer go through the Worker (`run_worker_first` lists only the API and document paths), so they stay free and don't count against the Worker's daily request allowance. A page load now costs two Worker requests (the gated HTML document and `GET /demo/identities`) instead of about five. Static assets add none. This is the same accounting the runbook and ADR-004 use.
6. **Deterministic MVP.** The Worker makes no model calls. If a later ADR approves AI, the model is called over HTTP from the Worker, and any Python-built context is precomputed in the Gold slice.

## Limitations of each choice

These limitations are accepted for the 2026-09-29 → 2026-10-31 window. Each row names what we lose, how much it matters now, what we do about it and when to revisit.

| Choice | Limitation | Impact in the window | Mitigation | Revisit when |
|---|---|---|---|---|
| JavaScript Worker | The team's strongest language is Python, and the #11 agent design is in Python. | Low. The MVP has no agent. | Business logic stays small and tested, and AI goes over HTTP. | A Python-only capability is proven necessary (see O2 and O4 below). |
| D1 (SQLite) | One writer per database; 500 MB per database on Free (10 GB on Paid); no row-level security, JSONB or rich types; limited query plans; region is a hint only. | None at this volume. | Indexed, customer-scoped queries; a per-episode row budget in CI; a single database. | Writes queue up (write p95 > 200 ms) or the database passes 5 GB. |
| Workers Free | 100,000 requests/day, 10 ms CPU per request, 50 D1 queries per invocation; `workers.dev` has no SLA. | Capacity is quantified in [ADR-004](ADR-004-intake-capacity-and-cost.md). | Assets served outside the Worker; weekly usage check. | Any daily limit above 70% for 3 days in a row → Workers Paid ($5/month). |
| Cloudflare Access | Free up to 50 users. It is a gate for the team and judges, not customer authentication. | None. | Allowlist the team and judges, or use one-time PIN. | More than 50 reviewers. |
| Basic gate and simulated identity | Not bank authentication. Anyone past Access can act as any demo customer. | Accepted for a synthetic demo. | Fixed allowlist; the README says so. | Any real-customer pilot needs real authentication in its own ADR. |
| Hashed bundles outside the Worker | Protected by Access only. | Low. Bundles contain code, not data. | HTML documents and every data route stay behind the gate. | Never serve data as a static file. |
| Gold slice | One business day, a customer allowlist, and at most 20 transactions per customer. | Demo coverage only; it doesn't represent the full dataset. | The manifest records the date, the files and the counts. | Multi-day or multi-customer slices, planned in the roadmap. |
| No Alembic | Forward-only migrations and no autogenerate. | Low. The schema is small. | Additive migrations tested against local D1; Time Travel for rollback. | The store moves to PostgreSQL. |
| Three places run code (browser, Worker, Python batch) | Contracts can drift between the Angular client and the Worker. | Medium. | JSON Schema contracts in `front-end/contracts/`, checked in back-end tests. | — |

## Consequences

- **+** One implementation of every business rule, deployed, tested and free for the whole window, with no cold starts when a judge opens the link.
- **+** A clear split between offline analytics (DuckDB) and online serving (SQLite/D1), with a single swap point if the store changes.
- **+** The adversarial test suite runs against the real runtime (local D1 through `wrangler dev`), not a stand-in.
- **−** Two languages in the repository: Python for data and JavaScript for serving.
- **−** Cloudflare-specific pieces (D1 bindings, Access, `wrangler`). Leaving Cloudflare means rewriting the store module and the deploy scripts.
- **−** Capacity claims stop at what ADR-004 measured. We make no production throughput claim.

## Implementation notes

- **Layout:**
  - `back-end/src/` is split into `index.js`, `router.js`, `http.js`, `auth/`, `modules/customer/`, `modules/agent/` and `store/d1.js`.
  - `front-end/src/app/` is split into `core/`, `features/customer/`, `features/agent/` and `shared/`.
  - The Gold slice lives in `data_pipelines/gold/`.
- **Deploy:** Cloudflare Workers Builds with root directory `back-end` and watch paths `back-end/**` and `front-end/**`. The D1 database and the secrets did not change.
- **Placement:** `placement.mode = "smart"` is adaptive. Cloudflare may run the Worker nearer D1 once telemetry shows a benefit, and the `cf-placement` response header reports where it ran. ADR-004 records measured locations only.
